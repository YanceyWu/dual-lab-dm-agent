## Goal

Align the synthetic demo database pipeline and the merged Dashboard legacy
surfaces so the sample DB reflects the current canonical staffing/contract
coverage authority model and the UI never renders raw `null` values as if they
were meaningful business output.

## Authorized outcome

The owner approved this bounded follow-on direction on 2026-08-06. Work may
proceed only in the ordered batches recorded below. The objective is to fix the
demo/Dashboard integration gap without changing approved business semantics or
using the synthetic demo to mask missing evidence.

## Current local state after Batch A/B follow-on

- the supported synthetic demo build path now publishes the canonical
  current-state staffing and canonical contract-coverage artifacts consumed by
  the merged Dashboard staffing / HIREF readers, so the raw sample DB is
  directly usable without post-build helper patch-up;
- the synthetic demo still intentionally keeps contract coverage `partial`
  because one STFTE member remains the designed missing-current-contract case,
  and some Project Health `unknown` / `not_available` states remain valid sample
  behavior rather than defects;
- the bounded HIREF follow-on distinguishes a missing current HIREF alert from
  an independently provable free slot under that supported partial state. This
  remains a conservative read-side inference only and is **not** a new
  canonical slot-occupancy publication model.

## Historical problem statement

Before Batch A/B and the bounded HIREF follow-on landed locally, the current
workbook branch had a real integration mismatch:

- the synthetic demo build produced the underlying workforce/capacity/health
  data, but the raw sample DB did not publish the canonical current-state
  staffing or contract-coverage artifacts that the merged Dashboard legacy
  surfaces read;
- demo characterization tests recovered from that gap by publishing helper
  artifacts after the DB was built, so the raw sample DB problem could escape
  branch-local validation;
- the Dashboard presentation layer rendered some backend `null` values directly
  instead of translating them into a display-safe placeholder;
- some synthetic Project Health `unknown` / `not_available` values remained
  deliberate and valid, so this slice had to preserve evidence-preserving
  semantics rather than forcing every field to become populated.

## Ordered batch plan

### Batch A — Synthetic demo pipeline alignment

Authorized scope:

- add raw-demo characterization that proves the sample DB generated by the
  supported demo build path is directly usable by the merged Dashboard without
  post-build helper publication;
- extend the supported synthetic demo pipeline so it publishes the canonical
  current-state staffing artifact required by the merged Dashboard staffing/team
  reads;
- extend the same supported synthetic demo pipeline so it publishes the
  canonical contract-coverage artifact required by the merged Dashboard HIREF /
  continuity-derived reads;
- keep the demo pipeline on approved capability contracts rather than relying on
  test-only patch-up behavior as the runtime source of truth.

Acceptance criteria:

- the raw sample DB produced by the supported demo build path reports a known,
  fresh current-state staffing summary through the Dashboard API;
- the raw sample DB exposes canonical team/member/load facts on the merged
  Dashboard legacy staffing/project surfaces without any post-build test helper;
- retained Project Health synthetic states stay unchanged where they are
  intentionally `unknown` / `not_available`.

### Batch B — Dashboard null-safe rendering

Authorized scope:

- normalize the merged Dashboard legacy rendering layer so `null` values are
  shown as `—` or `Unknown` instead of the literal string `null`;
- preserve the backend distinction between a meaningful zero and a suppressed /
  unavailable metric caused by freshness, partial coverage, or missing
  publication evidence;
- where the page already carries an approved freshness/coverage explanation,
  continue to surface that explanation instead of inventing replacement counts.

Acceptance criteria:

- no merged legacy Dashboard page shows a literal `null` value for the sample
  DB;
- partial or unknown contract/staffing coverage remains explicit rather than
  being converted into guessed numbers or false green status.

### Batch C — Documentation and consistency cleanup

Authorized scope:

- update operator/demo-facing docs so they distinguish:
  - fixed integration-gap `unknown` values caused by missing canonical
    publication; and
  - intentionally retained synthetic `unknown` / `not_available` health states;
- document that supported `partial` contract coverage does not automatically
  force all HIREF counts to `unknown`: missing-current alerts remain countable,
  and independently provable free slots remain countable only in the bounded
  supported partial mode;
- document that the free-slot inference remains conservative and does not create
  a new canonical slot-occupancy authority model;
- reconcile demo build/run/verification documentation with the final A/B
  behavior once those batches land.

Acceptance criteria:

- demo build instructions, sample-data guidance, and Dashboard usage guidance
  describe the same synthetic demo behavior and the same expected retained
  unknown states;
- no documentation implies that `partial` contract coverage means "no usable
  HIREF data" when the supported bounded rule can still prove alert/free-slot
  counts, and no documentation promises that every `unknown` will disappear;
- no documentation claims that the raw sample DB is Dashboard-ready unless that
  claim is true without post-build patch-up helpers.

## Rollback

Prefer a software-only rollback. The synthetic demo DB is rebuildable from an
empty target, so the supported rollback path is to revert the bounded software
change and regenerate the sample DB rather than preserving an incorrect
intermediate demo artifact.

## Risks and guardrails

- Do not let a test-only patch-up helper become the de facto production/demo
  runtime path without explicit approval.
- Do not replace evidence-driven `null` / `unknown` with guessed zeros, guessed
  counts, or green-looking placeholders.
- Do not “fix” retained Project Health synthetic states that are intentionally
  evidence-limited.
- Keep batches independently reviewable and reversible; do not blend the sample
  pipeline fix with an unrelated dashboard rewrite.
